# Server-scope inventory (Mission 5, D-03b)

Until Mission 4 every code path that acted for an already signed-in person but needed the database's help ran as the unrestricted **`server`** scope (the old
"system"). Mission 4 scoped the routes reachable without signing in. Mission 5 inventoried every remaining site, gave each a scope of its own, and made the
unrestricted scope unreachable from the application. This file is the record: what each site does, who can reach it, what it needs, what checks come first,
and the tests for both allowed and denied behaviour. (Counts: **71 application call sites + 3 in the middleware = 74** `runAsSystem` sites at the start of
the mission; the earlier "about 90" over-counted. Today the application has exactly **3** `runAsSystem` calls, each naming a narrow scope, and **0** uses of `server`.)

## Result in one paragraph

**Eliminated in the application, narrowed in the database, not closed.** No application code asks for `server` (static test `tests/serverScopeEliminated.test.ts`, and in
production `runAsSystem` without a narrow scope throws); the database can be told to refuse `server` for good (`npm run identity:enforce -- server-scope off`, migration 0029), and the
whole browser suite runs with it refused (`npm run test:e2e:noserver`). Eleven new scopes replace it, each opened to named tables **and operations** only. What remains
open is described under "What is still broad" below: three scopes (`staff`, `review`, `mfa`) are authorised in code by the acting person's permissions, not in the database,
because the assertion names a scope, not the person who asked. D-03b is therefore **narrowed and enforceable, not closed**.

## How the sites were found and classified

`grep runAsSystem server` (74 sites), then for each: the route or caller (read, not guessed), whether an unauthenticated caller can reach it, the SQL it issues (recorded by running the
whole suite with the work labelled by the scope it asked for, then reading the statements per scope), and the check that comes first. The traced matrix gave
the first grants; a leave-one-out run (each grant removed in turn, the scenario and route tests re-run, plus a detector that fails a test when a best-effort write
swallows its own error) removed what nothing used. See "Verification".

Rules the code now follows (`server/dbContext.ts`):
* `withScope(scope, fn)` gives exactly `scope` and cannot be asked for `server` (type-level).
* Inside a public or background **entry** scope (`auth`, `invite`, `session`, `scheduler`, `webhook`, `ratelimit`) a helper may only *narrow* to the scopes in `ENTRY_MAY_USE`
  (each a subset of the entry scope; `tests/narrowScopes.test.ts` checks the subset property against the database). Anything else it asks for stays in the entry scope, so
  an unauthenticated route can never be moved onto a wider scope by a helper.
* Why a signed-in helper *swaps* rather than inherits: a block-list lookup run inside an invitation redeem must see the block list; staying in the caller's narrower scope
  showed it nothing, and "no rows" reads as "not blocked" (found by `pairingInvitations.test.ts` during this work, then fixed).

## What is still broad, exactly, and why

1. **`staff` cannot be limited by organization in the database.** The assertion names a scope, not the staff member, so a policy cannot say "only the patients of *my* organization".
   The database limits staff to the tables above and the operations listed (no clinical record tables except appointments' times and pairing status); the choice of **which** rows is made by
   `orgs.access` + `scopeFor` in `server/services/orgs.ts` (membership, permission matrix, patient's `orgStaffVisible`), attacked from outside by `orgs.test.ts` and `reviewFindings.test.ts`.
   Constraint on the code path: every function starts from `orgs.access`; input is bound parameters; duration is one request (the assertion lives ≤ 60 s and one transaction).
   **Closing it** needs the acting person in the assertion (`system.staff:<userId>` verified by the database, policies joining `org_memberships`). That is a design change to the assertion format and
   every staff query; it is the recommended next step (decision D-03c), not done here.
2. **`review` can update any account row, doctor profile and credential.** It is used only by administrators' decisions behind `adminOnly` (role read live + second factor). Same closing step: put the
   administrator's id in the assertion and let policies check `app_is_admin()` for that id.
3. **`mfa` can read and rewrite any person's second-factor state**, reached by the sign-in challenge steps and an administrator's reset. The challenge token and the lock-out rules are enforced in code (`mfaService`).
4. **`ops` can read (not write) reminder and delivery rows**, though the code returns only counts. A `SECURITY DEFINER` counts-only view would remove even that; not done.
5. **The reach of a full code-execution compromise of the application is unchanged**: it holds the signing key and can sign any of these scopes, or any person. Narrow scopes limit *injection*, not that.

## Verification

* `tests/narrowScopes.test.ts` — the declared permissions equal the database's policies; **every select/insert/update/delete outside a scope's grant is refused for every scope on every table**
  (several thousand statements, each run inside a transaction that is rolled back); the sensitive tables are in no new scope; an edited, replayed or invented scope is nobody; a person gets none of the scoped
  functions; role confusion on `/api/admin` and `/api/orgs`; concurrent suspension, concurrent staff revocation, and a single-use link spent by many simultaneous requests.
* `tests/serverScopeEliminated.test.ts` — static scan, production guard, and the application's sign-up, sign-in, recovery, connection, messaging, booking, end-of-connection, clinician registration and approval,
  organization, invitation, scheduler and pairing-code flows with the database **refusing** `server`.
* `npm run test:e2e:noserver` — the whole browser suite (restricted role) with `server` refused.
* Leave-one-out (79 policies = 42 table/scope pairs; each pair removed whole, and again with only its write commands removed; the scope's scenario and route tests re-run with the best-effort-write detector on): **59 runs failed when a grant was removed (needed)** and 8 pairs did not: `doctor_profiles`/`ops`, `job_runs`/`ops`, `personal_reminders`/`ops`, `personal_reminder_deliveries`/`ops`, `reminder_deliveries`/`ops`, `users`/`pairing`, `doctor_profiles`/`pairing`, and the update on `users`/`review`. The `ops` and `users` ones are used by code that reports zero when it sees nothing; `tests/scopeEffects.test.ts` was written so that removing them fails (each removal tried), after which they count as needed. `reminder_deliveries`/`ops` is redundant (visible through the reminder, by its own policy) and was removed; `doctor_profiles`/`pairing` failed the full suite and stayed.
* Defects this work found and fixed. **Reproduced first, then fixed:** a password-reset link usable by many simultaneous requests (single use was check-then-act: 8 of 8 succeeded); organization staff revocation applied and
  audited twice by two simultaneous requests; a fail-open block check (a helper swapped into a narrower scope saw no block list). **Hardened without a reproduction:** a care-circle invitation is now accepted by a
  conditional update and a lost account-creation race answers "invalid link" (the concurrent test passes with and without the conditional update, so it does not prove that part; the account-creation conflict is covered).
  **Found by reading, fixed:** organization staff received a password hash from every account lookup (now an id only).
* Lesson recorded: a grant that looked unused to the leave-one-out run (`doctor_profiles`/`pairing`) was needed by a test the run did not include (`reviewFindings`), and several read-only grants (the operations counts, the
  readiness check) look unused because missing rows read as zero, not as an error. The full suite is run after every trim, and `tests/scopeEffects.test.ts` now fails if those grants are removed (checked by removing each one).


## Mission 7: the acting person (migration 0030)

The `staff` scope's 26 sites split. The 16 inside functions that hold an `OrgAccess` (and `access()`, which mints it) moved to the new **`orgmember`** scope, whose assertion carries the acting person and whose policies require that person to be an active
member of the organization a row belongs to. The other 10 stay on `staff` (no actor: a single-use token or the person's own id is the authority). `mfa` (10 sites) and `review` (10 sites) keep their call sites; their policies now require the verified
actor to be the account holder, or an active administrator. `auth` lost its direct access to the second-factor tables. Totals now: 10 `staff`, 16 `orgmember`, 10 `review`, 10 `mfa`. Details and residual: `docs/LAUNCH_GATES.md` (D-03c).
